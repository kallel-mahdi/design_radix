## Research Findings

### Zotero Search Architecture

**Source**: `zotero/chrome/content/zotero/xpcom/data/search.js`, `searchConditions.js`, `fulltext.js`

**Key Insights**:
1. **Two-Tier Search**: Quick search (toolbar) vs Advanced search (dialog)
2. **Quick Search Modes**:
   - `titleCreatorYear`: Title, publicationTitle, shortTitle, year, creators
   - `fields`: All fields + tags + notes + annotations
   - `everything`: fields + full-text PDF content
3. **Search Logic**: Multiple terms use AND between blocks, OR within each block
4. **Full-Text Indexing**: Word tokenization with SQLite FTS, stores in separate tables

**Our Adaptation**:
- MVP: Single search mode (similar to `titleCreatorYear`)
- Use MongoDB `$text` index instead of custom word tokenization
- No full-text PDF search in MVP (Phase 2)

### MongoDB Search Best Practices

**Sources**:
- [MongoDB text index vs regex - DEV Community](https://dev.to/ahmedossama22dev/mongodb-text-index-vs-regex-for-text-searching-1opk)
- [Speed up MongoDB Regex Queries - Medium](https://medium.com/statuscode/how-to-speed-up-mongodb-regex-queries-by-a-factor-of-up-to-10-73995435c606)

**Key Insights**:
1. **Text Search** (`$text`): O(log n) with index, tokenizes and stems content
2. **Regex Search**: O(n) collection scan, only fast with `^` prefix anchor
3. **Recommendation**: Use `$text` for keyword search, combine with regex for substring matching
4. **Limitation**: MongoDB `$text` doesn't support partial word matches (e.g., "cat" won't match "bobcat")

**Our Approach**:
- Primary: MongoDB `$text` index with weighted fields
- Filters: Standard MongoDB queries (`$match`, `$gte`, `$lte`)
- Facets: Aggregation pipeline for counts

### @retorquere/bibtex-parser Library

**Sources**:
- [NPM Package](https://www.npmjs.com/package/@retorquere/bibtex-parser)
- [GitHub Repository](https://github.com/retorquere/bibtex-parser)
- [Documentation](https://retorque.re/bibtex-parser/)

**Key Features**:
- Powers Better BibTeX for Zotero (battle-tested)
- Handles LaTeX commands (`\textbf`, `\textsc`) → Unicode
- Cross-reference inheritance support
- TypeScript types included
- Async parsing for large files

**API Structure**:
```typescript
import { parse, parseAsync } from '@retorquere/bibtex-parser';

const result = parse(bibtexString, options);
// result.entries: Entry[] - parsed bibliography entries
// result.errors: Error[] - parsing errors
// result.strings: Record<string, string> - @string macros
```

## Architecture Decisions

### Decision 1: Keyboard Shortcut Implementation

**Options**:
- A: Inline handlers in each component (current partial approach)
- B: Centralized `useKeyboardShortcuts` hook mounted in AppLayout

**Choice**: B - Centralized hook

**Rationale**:
- Single source of truth for all shortcuts
- Easier to maintain and extend
- Prevents duplicate event listeners
- Matches Zotero's approach (centralized keyboard handling)

---

### Decision 2: Search Strategy

**Options**:
- A: MongoDB `$text` index (recommended by research)
- B: Regex-based queries
- C: MongoDB Atlas Search

**Choice**: A - MongoDB `$text` index

**Rationale**:
- O(log n) vs O(n) for regex
- Built-in stemming and tokenization
- No external service dependency (unlike Atlas Search)
- Sufficient for MVP scope

---

### Decision 3: BibTeX Parser Library

**Choice**: `@retorquere/bibtex-parser`

**Rationale**:
- Battle-tested (powers Zotero's Better BibTeX)
- Handles complex BibTeX features (cross-refs, macros, LaTeX escapes)
- TypeScript support
- Async parsing for large files

## Deviations from Zotero

### 1. Simplified Search Modes

**Zotero**: Three search modes (titleCreatorYear, fields, everything)
**Ours**: Single search mode (equivalent to `titleCreatorYear`)
**Rationale**: Simpler UX for MVP, can add modes in Phase 2

### 2. No Full-Text PDF Search

**Zotero**: Indexes PDF content with custom word tokenization
**Ours**: Metadata search only (title, authors, abstract, venue)
**Rationale**: PDF text extraction requires additional infrastructure

### 3. Simplified Advanced Filters

**Zotero**: Complex boolean operators (AND/OR/NOT per condition)
**Ours**: Simple AND logic for all filters
**Rationale**: Covers 95% of use cases without complexity
